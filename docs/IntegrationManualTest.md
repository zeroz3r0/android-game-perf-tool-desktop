# Auto-Updater — Manual Integration Test

This document captures **reproducible manual checks** for the auto-updater shell scripts
generated by `AutoUpdater.kt`. These checks intentionally live OUTSIDE JUnit because:

1. The script involves a real `bash` subprocess that backgrounds a relauncher.
2. The `open -n` / `nohup java -jar` relaunch lines have OS-specific side effects.
3. JUnit tests for them would be flaky (timing, process tree, file locks).

For the **detection logic**, see `AutoUpdaterDetectionTest.kt` (9 unit tests, fully automated).

---

## 1. Script generation — fat JAR (no real install required)

Goal: verify the generated `.gameperf-update.sh` does the right thing in isolation,
without ever touching the user's real installation.

### 1a. Create a fake fat-JAR install

```bash
mkdir -p /tmp/gameperf-test/fatjar
cd /tmp/gameperf-test/fatjar

# Fake "current" JAR
echo "OLD_JAR_CONTENT_v1" > GamePerf.jar

# Fake "downloaded" JAR (simulating what AutoUpdater.downloadUpdate produced)
echo "NEW_JAR_CONTENT_v2" > GamePerf.jar.new
```

### 1b. Build the script by hand (mirrors `createUnixUpdateScript`)

```bash
cat > /tmp/gameperf-test/fatjar/.gameperf-update.sh <<'SCRIPT'
#!/bin/bash
set -e
LOG="$HOME/GamePerf Reports/updates/last-update.log"
mkdir -p "$(dirname "$LOG")" 2>/dev/null || true
exec >> "$LOG" 2>&1
trap 'rm -f "/tmp/gameperf-test/fatjar/.gameperf-update.sh"' EXIT
echo "=== [$(date '+%Y-%m-%d %H:%M:%S')] Update script started ==="
sleep 2
if [ ! -s "/tmp/gameperf-test/fatjar/GamePerf.jar.new" ]; then
  echo "FATAL: new JAR does not exist or is empty"
  exit 1
fi
if [ -f "/tmp/gameperf-test/fatjar/GamePerf.jar.bak" ]; then
  rm -f "/tmp/gameperf-test/fatjar/GamePerf.jar.bak"
fi
mv -f "/tmp/gameperf-test/fatjar/GamePerf.jar" "/tmp/gameperf-test/fatjar/GamePerf.jar.bak"
mv -f "/tmp/gameperf-test/fatjar/GamePerf.jar.new" "/tmp/gameperf-test/fatjar/GamePerf.jar"
echo "Relaunch step would run here (skipped in dry-run)"
echo "=== Done ==="
SCRIPT
chmod +x /tmp/gameperf-test/fatjar/.gameperf-update.sh
```

### 1c. Run and verify

```bash
bash /tmp/gameperf-test/fatjar/.gameperf-update.sh
sleep 3

# All three checks must pass:
test "$(cat /tmp/gameperf-test/fatjar/GamePerf.jar)" = "NEW_JAR_CONTENT_v2"   && echo "OK new in place"
test "$(cat /tmp/gameperf-test/fatjar/GamePerf.jar.bak)" = "OLD_JAR_CONTENT_v1" && echo "OK backup preserved"
test ! -f /tmp/gameperf-test/fatjar/.gameperf-update.sh                       && echo "OK script self-deleted"

# Inspect the log
tail -20 "$HOME/GamePerf Reports/updates/last-update.log"

# Cleanup
rm -rf /tmp/gameperf-test
```

Expected: all three `OK` lines print, and the log shows the timestamped progression.

## 2. Script generation — macOS .app bundle relaunch

Goal: verify `open -n <bundleRoot>` re-launches the bundle correctly through its native
launcher (which is the whole point of the fix — `nohup java -jar` skips the bundle's
JVM options like `-Dskiko.library.path` and crashes Compose Desktop on startup).

### 2a. Pre-flight: confirm `open -n` works for any .app

```bash
# Use any installed .app — Calculator is shipped with macOS.
open -n /System/Applications/Calculator.app
```

A *new* Calculator window must appear (the `-n` flag forces a new instance).
Close it.

### 2b. Real-installation smoke test (only if you have GamePerf.app installed)

> **DESTRUCTIVE**: this writes to your actual `/Applications/GamePerf.app`.
> Make a backup first if you care about the current install.

```bash
# 1. Locate the bundle's main JAR
JAR=$(ls /Applications/GamePerf.app/Contents/app/android-game-perf-tool-desktop-*.jar | head -1)
echo "Current JAR: $JAR"
echo "Size:        $(stat -f%z "$JAR") bytes"

# 2. Verify the launcher exists and is executable
ls -l /Applications/GamePerf.app/Contents/MacOS/GamePerf
test -x /Applications/GamePerf.app/Contents/MacOS/GamePerf && echo "OK launcher executable"

# 3. Test the relaunch command in isolation (no JAR replacement)
open -n /Applications/GamePerf.app
```

Expected:
- A *new* GamePerf window opens (the `-n` flag bypasses single-instance lock).
- No `UnsatisfiedLinkError` in `~/Library/Logs/GamePerf/` or `Console.app`.
- No `NoClassDefFoundError`.
- The window renders normally (Skiko/Compose initialized correctly).

If this works, the auto-updater's macOS branch will work end-to-end, since the only
new ingredient over the verified mv-script is exactly this `open -n` line.

### 2c. End-to-end (full update cycle, requires a real new release)

```bash
# Launch the installed app
open /Applications/GamePerf.app

# Inside the app: Settings → Buscar actualización → Descargar e instalar
# The app should:
#   1. Download the new JAR from GitHub Releases
#   2. Detect MACOS_APP_BUNDLE via detectInstallation()
#   3. Validate the JAR is ≥ 50 MB (uber-JAR)
#   4. Run .gameperf-update.sh which:
#      - Backs up current JAR → .bak
#      - Replaces with new JAR
#      - Runs `open -n /Applications/GamePerf.app`
#      - Self-deletes
#   5. New version starts; old process exits.
```

After the update, verify:

```bash
# The log should show the full sequence
cat "$HOME/GamePerf Reports/updates/last-update.log"

# The .bak should exist with the old JAR
ls -la /Applications/GamePerf.app/Contents/app/*.jar*

# The script should be gone
test ! -f /Applications/GamePerf.app/Contents/app/.gameperf-update.sh && echo "OK script cleaned up"
```

## 3. Failure modes to verify manually

| Scenario                                    | Expected outcome                                                                                  |
|---------------------------------------------|---------------------------------------------------------------------------------------------------|
| Downloaded JAR is < 50 MB                   | `applyUpdateMacOSBundle` throws `IllegalStateException` BEFORE touching disk                      |
| Download interrupted, .new file empty       | Script exits with `FATAL: new JAR does not exist or is empty`, original JAR is untouched          |
| `Contents/MacOS/GamePerf` removed manually  | `detectInstallation` returns `FAT_JAR_STANDALONE` (defensive fallback), update path differs       |
| Script crashes mid-relaunch                 | `trap EXIT` still removes `.gameperf-update.sh`; user just relaunches manually from Applications/ |

## 4. Where the unit tests live

For deterministic, fast checks of the **detection logic** (which is the bulk of the fix),
see `src/test/kotlin/com/gameperf/desktop/core/AutoUpdaterDetectionTest.kt`. It covers:

- `DEV_MODE` when no JAR is detectable
- `FAT_JAR_STANDALONE` for jars outside any bundle
- `MACOS_APP_BUNDLE` for a complete `.app` layout
- Fallback to `FAT_JAR_STANDALONE` when launcher is missing
- Fallback to `FAT_JAR_STANDALONE` when launcher exists but is not executable
- `WINDOWS_APP_BUNDLE` for `MyApp/app/main.jar` + `MyApp/MyApp.exe`
- Defensive fallback when sibling `.exe` is missing
- `LINUX_NATIVE_PACKAGE` with launcher in `bin/<name>`
- `LINUX_NATIVE_PACKAGE` without launcher (null launcher field)

Run them with:

```bash
./gradlew test --tests "com.gameperf.desktop.core.AutoUpdaterDetectionTest"
```
